# Product Factory 개발 우선순위와 자동 작업 범위

기준일 2026-10-08. 새 제품 제작과 Factory 등록·측정을 반복할 수 있도록 개발 순서를 정한다. 현재 Registry, Ideas, 주간 Pipeline, 수동 Sync, 상태·stale 판정, 수익 화면과 PDF 내보내기는 구현돼 있다. 아래 작업은 기존 기능을 확장한다.

코드·fixture 개발과 실제 운영 연결의 완료를 구분한다. 로컬에서 기능을 검증해도 공급자 report, 운영 저장, Dashboard 반영과 예정 수집까지 검증하기 전에는 실운영 완료로 기록하지 않는다.

## 1 개발 우선순위

| 순서 | 작업                            | 개발할 범위                                                                                                     | 완료 기준                                                                                           | 자동 개발 범위                                                                                |
| ---- | ------------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 1    | F01 제품 등록 도우미            | 기존 Add/Edit product를 단계별로 안내. 제품 정보, 공급자 식별자, Active와 Status 차이, 준비 체크와 가이드 링크  | 신규·기존 제품 흐름 유지, ID 오류·중복 등록 처리, 준비 전 Active의 의미를 안내                      | 기존 API와 fixture로 전체 구현 가능                                                           |
| 2    | F02 연결 진단과 다음 행동       | 기존 integration·health·sync 이력을 모아 제품별 미설정·미실행·실패·partial·지연과 해결 행동 표시                | enabled를 성공으로 표현하지 않음. 0행 성공·실제 0·미수집 구분, 원본 실행·기간·오류로 이동           | Registry·integration·metric·run의 기존 읽기 데이터로 구현. 확인 불가한 인증·job 상태는 미확인 |
| 3    | F03 제품 metadata 등록 미리보기 | 제작 가이드의 JSON을 읽어 검증·필드 대응·기존 제품 충돌 미리보기 후 기존 등록 폼에 채움                         | 파일 읽기만으로 저장하지 않음. 새 제품·기존 제품을 구분하고 편집할 필드 확인. 매핑·상태·Active 보존 | 서버 스키마 변경 없이 구현. 실제 운영 등록은 수행하지 않음                                    |
| 4    | F04 운영 문제 목록              | 기존 stale·실패·미연결·coverage 판정을 재사용해 전체 제품의 문제, 심각도, 마지막 성공과 다음 행동을 한곳에 표시 | 중복 문제 통합, 정상·미확인 구분, 제품·run 이동, 모바일 표시                                        | 앱 내부 표시까지. 외부 메시지 발송·상시 백그라운드 감시는 별도 단계                           |
| 5    | F05 출시 준비 체크리스트        | 제품별 SEO·태그·핵심 이벤트·검색 등록·정책·배포 증거·Factory 연결의 상태와 확인일 관리                          | 자동 관측과 수동 확인 구분. 준비/미확인/대기 및 근거 표시, 편집·저장 후 복구                        | UI와 저장 계약·migration·RLS의 로컬 검증. 운영 migration 적용은 제외                          |
| 6    | F06 주간 운영 리포트            | 기존 집계·export를 재사용해 제품별 변화, 데이터 누락, 주요 문제와 이번 주 확인할 행동을 요약                    | 일일 users 합계를 기간 unique로 오인하지 않음. 통화·기간·부분 수집 표시, 원본으로 이동              | 결정적 계산과 로컬 미리보기·내보내기. 유료 AI와 외부 자동 발송은 제외                         |
| 7    | F07 제품별 개선 작업 보드       | 문제·아이디어·실험을 제품의 작업으로 관리하고 기존 Week/Pipeline에 연결                                         | 담당·상태·우선순위·완료 증거, 작업과 사업 상태/Active의 독립성 유지                                 | UI·API·migration·RLS와 fixture 개발. 운영 적용은 별도                                         |
| 8    | F08 출시 후 평가 지원           | 제품별 성공 목표·기간과 실제 지표를 비교해 HOLD/IMPROVE/SCALE 판단 근거 제시                                    | 데이터 부족이면 판단 보류, 기준·근거·확인자 기록. 제품 상태 자동 변경 없음                          | F06/F07의 데이터 계약이 정해진 뒤 개발                                                        |

F01/F02를 먼저 만들면 새 제품을 어떻게 준비하고 어떤 연결 문제를 해결해야 하는지 명확해진다. F03은 문서에 적은 제품 정보를 다시 입력하는 부담을 줄인다. F04 이후는 실제 제품과 지표가 늘 때 운영 효율을 높인다.

## 2 자동 개발에 함께 포함할 기술 작업

| 작업                       | 목적                                                      | 완료 기준                                                                                                                     |
| -------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| T01 OAuth helper 출력 보호 | 현재 helper가 refresh token을 stdout에 출력하는 문제 개선 | 성공·실패·예외와 테스트 로그에 token/secret이 남지 않음. 보호된 전달 방식과 본인 실행 절차 문서화. 실제 OAuth는 실행하지 않음 |
| T02 기능 검증과 CI 준비    | 새 기능의 실패를 로컬에서 재현하고 검증 결과를 남김       | 기능별 의미 있는 테스트와 fixture, lint·typecheck·unit·필요한 DB/browser·build 통과. Windows 줄바꿈 검사와 기존 경고 구분     |
| T03 배포와 변경 영향 기록  | 다음 사람이 기능을 적용할 수 있게 준비                    | UI/API/schema 변경 목록, 적용 순서, 원복 조건, 설정 필요 항목 정리. Pages와 Edge 배포의 구분 유지                             |

T01은 공통 인증을 사용하는 자동 작업 전에 우선 처리한다. T02/T03은 각 기능에 포함한다. 전체 의존성 업그레이드나 앱 프레임워크 전환은 이 개발 묶음의 범위가 아니다.

## 3 오늘 우선 맡길 개발 묶음

첫 묶음은 **T01 → F01 → F02 → F03** 순서다. 완료한 기능마다 검증과 checkpoint를 남기고 다음 작업으로 이동한다. 첫 묶음이 통과하면 F04까지 이어갈 수 있다. F05/F07은 영속 저장을 위해 데이터 계약 검토가 필요하므로 화면 초안만 보고 완료로 판정하지 않는다.

기존 health·insights·API·form을 재사용한다. F02와 F04가 각각 다른 상태 판정 규칙을 만들지 않도록 같은 모델을 공유한다. F03의 JSON도 [제작과 연결 가이드](PRODUCT_CREATION_AND_FACTORY_ONBOARDING.md)에 있는 제안 형식과 맞추고, 실제 API 스키마로 변환하는 단계를 명시한다.

### 기능별 필수 검증

- F01: 유효 등록, 잘못된 공급자 ID, 기존 제품 편집, 서버 validation 오류, 모바일 폼, Active 기본 처리.
- F02/F04: 미연결, enabled지만 미실행, 0행 성공, 정상 실측 0, partial, 반복 실패, 지연, 읽기 실패와 실행 중 상태.
- F03: 깨진 JSON, 지원 형식 불일치, Registry 중복, 필드 누락, 기존 AdSense 매핑 보호, 적용 전 취소, 입력 파일의 Secret 배제.
- T01: 성공 응답·provider 오류·예외의 로그에서 Secret 부재, 테스트 대역으로 보호된 전달 검증.
- 공통: 원래 Products/Ideas/Week/Revenue/Sync 기능의 회귀 검증, 신규 기능의 desktop/mobile 화면 확인.

F03에서 현재 관리하지 않는 필드는 무시 여부를 명확히 표시한다. 파일에 있는 상태·Active를 무조건 적용하거나 기존 제품의 수집 식별자를 조용히 덮어쓰지 않는다.

## 4 실제 운영에서 별도로 확인할 항목

다음은 개발 기능과 구분해 운영 인수 작업으로 남긴다.

1. 기존 관리자 로그인과 MFA 이후 실제 dashboard 읽기 확인.
2. P001 운영 검증 완료 기록과 현재 환경의 Sync 0건 상태 대조.
3. 공통 인증 계정의 해당 GA4/GSC/Bing/AdSense 접근권한 확인.
4. 준비된 공급자 하나의 실제 report → 저장 → Dashboard 대조.
5. 기존 자동화 인증과 준비된 job 하나의 실제 예정 수집 확인.
6. 필요할 때 localhost용 CORS·Auth 설정을 기존 운영 origin과 함께 검토.

기능 개발 중 새 Factory·Supabase 프로젝트, 운영 DB 초기화, 실수집 호출, 공통 job 활성화, Secret 재발급, 관리자·MFA 변경, 배포를 자동으로 수행하지 않는다. 외부 알림 채널을 구현하더라도 실제 메시지 발송은 별도 요청 범위에서 진행한다.

## 5 자동 개발에 전달할 작업 지시문

아래 범위는 개발을 맡길 때 사용할 수 있다. 이 문서 생성만으로 개발을 실행한 것은 아니다.

```text
기존 Product Factory에서 T01 → F01 → F02 → F03 순서로 로컬 개발하라.
docs/DEVELOPMENT_PRIORITIES.md의 범위·완료 기준과
docs/PRODUCT_CREATION_AND_FACTORY_ONBOARDING.md의 등록·수집 계약을 따르라.

기존 Git 상태와 미커밋 변경을 먼저 확인하고 보존하라.
앱 소스·기존 form/API/health/insights를 읽고 재사용하라.
작업 브랜치는 codex/ 접두어를 사용하고, 원래 변경을 임의 commit에 섞지 마라.
각 기능을 구현한 뒤 해당 기능 테스트와 필요한 회귀 검증을 완료하라.
첫 묶음이 통과하면 F04를 이어서 개발하라.

운영 DB·Auth·Secret·cron·배포는 변경하지 마라.
실제 공급자 Sync/OAuth·외부 메시지 발송은 실행하지 마라.
새 프로젝트 생성이나 기존 제품 재등록을 하지 마라.
C:\AI-Agent 공용 core와 다른 작업·프로세스를 변경하거나 중단하지 마라.
비밀번호·MFA·token·Secret 값을 출력하거나 요구하지 마라.

미확인 운영 상태를 연결 성공으로 표현하지 마라.
인증이 필요한 운영 검증에 막히면 그 항목만 남기고 독립적인 개발을 계속하라.
지속되는 테스트 실패나 설계 의존성을 checkpoint와 다음 행동으로 기록하라.
완료한 기능·테스트·화면·변경 파일·적용 조건·남은 작업을 보고하라.
fixture 성공과 실운영 성공을 구분하고 push·merge·배포는 하지 마라.
```

## 6 이후 개발의 의존 관계

F01 등록 도우미 → F03 metadata 미리보기 → F05 출시 체크리스트 순으로 제품 준비를 연결한다. F02 진단 → F04 문제 목록 → F07 개선 작업 보드로 문제를 실행 가능한 작업으로 연결한다. F06 운영 리포트와 F07의 실험 결과를 확보한 뒤 F08 평가 지원을 추가한다.

제품 Starter 자동 생성기, AI 아이디어 생성, 결제·팀 기능, P002 서비스 개발, Harness/core 개선은 후속 범위를 별도로 정한다. 지금의 우선순위는 기존 Factory에 제품을 정확히 등록하고 수집 상태와 다음 행동을 이해할 수 있게 만드는 것이다.
